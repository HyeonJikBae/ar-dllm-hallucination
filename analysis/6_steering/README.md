# 6. Steering: 아는데 틀린 답을 정답으로 바꾸기 (Dream-v0-Base-7B)

대상은 **아는데 틀린 질문**이다. 같은 사실을 묻는 질문 5개 중 1~4개만 맞히는 사실(1/5~4/5, 1,190개 사실, 5,950행)에서 틀린 질문을 말한다.

질문을 바꾸지 않고, 모델 내부의 hidden state에 방향을 더해 정답으로 바뀌는지 본다.

## 공통 설정
- **개입 위치**: layer 20 출력, 프롬프트 마지막 토큰(`...\nAnswer:`의 끝).
  - 디노이징 32번 forward마다 매번 개입한다. 일부 초기 스크립트는 처음 8번에만 개입한다(`T=8`).
- **방향을 만드는 데이터**: 같은 위치의 step-0 상태(답 칸이 아무것도 채워지기 전). `data/1_raw/dream_hidden_steps/hid_prompt_last.npy`의 `[:, 0]`이다.
- **생성 설정**: 데이터와 같다. 캔버스 32칸, 32 step, `topk_margin`, 온도 0.
- **채점**: 새 답을 repo 규칙으로 채점한다(`run_grading.is_correct`). 유형이 필요한 스크립트는 `classify_rules.classify`를 쓴다.
- **교차 적합**: 주어(subject)를 5묶음으로 나눈다(`order % 5`, seed 0으로 섞음). 한 묶음의 행에는 나머지 4묶음으로 만든 방향만 쓴다. 그래서 방향을 만든 행과 평가하는 행이 겹치지 않는다.
- **세기**: `c × mean‖h‖`. mean‖h‖는 약 54이고, c는 0.5나 1을 쓴다.
- **배치 주의**: 같은 배치 구성이면 답이 결정적으로 같다. 하지만 bf16 수치 때문에 배치 구성이 바뀌면 개입 없이도 답의 약 15%가 저장된 답과 달라진다.
  - 그래서 모든 실험은 같은 배치 구성의 "개입 없음" 실행(`base`)과 비교한다.
  - 저장된 답과 같은 배치(같은 프롬프트 길이 64개)로 돌리면 310/310 그대로 재현된다(`pad64_pipeline.py`).
- **실행**: repo 루트에서 `CUDA_VISIBLE_DEVICES=<gpu> python3 analysis/6_steering/<script>.py`. CPU 전용 스크립트는 docstring에 적혀 있다.

## 결론
1. **같은 사실 안에서 구한 평균 차이 방향(B)으로 밀면, 틀린 질문의 약 4분의 1이 정답이 된다.** 의미 없는 방향은 약 9%였다.
2. **SAE latent를 고르거나 빼거나 더하는 방식은 크기를 맞춘 무작위 latent보다 낫지 않았다.**
3. 맞던 질문도 밀면 일부 틀린다. 그래서 모든 질문에 밀면 순이득이 작다(47.6% → 49.2%).
   - 틀린 질문에만 밀 수 있다면 60.0%까지 간다.
   - 지금 병목은 방향이 아니라 **어느 질문이 틀릴지 미리 아는 것**이다.

## 1. 방향 B (평균 차이를 더하기, CAA)
**만드는 법** (`caa_all_rows.py`가 `B_directions.npy`로 저장, fold마다 하나씩 [5, 3584]):
```
평가할 묶음 g를 뺀 나머지 4묶음, 1/5~4/5 사실 중 정답 행과 broken 행이 둘 다 있는 사실마다
    d_f = mean(정답 행의 h) - mean(broken 행의 h)
B[g] = unit( mean_f d_f )            # 사실마다 차이를 먼저 구하고 평균 → 사실별 주어·관계·난이도가 빠진다
개입:  h[prompt_end] += c * 54 * B[g]   # 32번 forward 모두
```
사실을 섞어서 `mean(모든 정답) - mean(모든 오답)`으로 구하면(방향 A) 1/5~4/5 사이의 앎 정도 차이가 섞여서 효과가 약하다.

**결과** (원래 틀린 질문이 정답으로 바뀐 비율, `caa_directions.py`):

| 방향 (c=1) | broken 310행 | entity 300행 | 원래 맞던 300행이 계속 맞음 |
|---|---|---|---|
| 개입 없음 | 3.2% | 6.0% | 94.3% |
| **B** = 정답 − broken | **25.2%** | **27.0%** | 69.7% |
| E = 정답 − entity | 23.5% | 23.7% | 69.7% |
| B+E | 25.5% | 25.0% | 70.7% |
| C = entity − broken | 23.5% | 18.0% | 64.7% |
| 의미 없는 방향 D (broken 행을 무작위 반반으로 나눈 평균 차이, 4회) | 5.6% | 12.3% | 49.0% |

- B와 E는 cosine 0.83으로 거의 같은 방향이다. 그래서 이후 실험은 **오답 유형을 나누지 않고 정답/오답**으로만 본다.
- c=0.5에서는 broken 19.0%, entity 22.0%가 정답이 되고, 맞던 질문은 83.0%가 유지된다.
- c를 1.5, 2로 키우면 broken에서 정답이 21.9%, 12.6%로 줄고 entity 오답이 늘어난다(`caa_followup.py`).
- 사실을 섞은 방향 A는 최대 12.3%였다. 크기를 맞춘 무작위 SAE latent 합 방향은 평균 7.4%(최대 11.9%)였다(`caa_broken.py`).

**전체 적용** (`caa_all_rows.py`). 1/5~4/5의 5,950행 전부와 0/5, 5/5에서 각 1,000행을 돌렸다.

| | 1/5~4/5 정답률 |
|---|---|
| 개입 없음 | 47.6% |
| 모두 밀기, c=0.5 | 49.2% (고침 582, 망침 487) |
| 모두 밀기, c=1 | 45.6% (고침 737, 망침 860) |
| 틀린 질문만 밀기(오라클), c=0.5 / c=1 | 57.4% / **60.0%** |

k별로 보면(c=1, 원래 → 틀린 질문만 밀기):
- 1/5: 19.1% → 31.2%
- 2/5: 39.7% → 55.6%
- 3/5: 59.3% → 74.4%
- 4/5: 79.2% → 87.3%

0/5는 밀어도 0.2%에서 1.2%로만 오른다(모르는 사실은 못 고친다). 5/5는 99.5%에서 91.8%로 떨어진다.

## 2. 게이팅: 틀릴 질문만 골라 밀기
한 행의 개입은 같은 배치의 다른 행에 영향을 주지 않는다. 그래서 "고른 행은 민 결과, 나머지는 개입 없음 결과"로 오프라인 시뮬레이션을 한다.

- `gate_detectors.py`: step-0 상태로 만든 예측기를 같은 5묶음으로 교차 적합하고, 점수를 `gate_scores.npz`에 저장한다(CPU).
  - P_all (정답/오답, 전체 행으로 학습): 전체 AUROC 0.936, 1/5~4/5 안에서는 0.646.
  - P_mid (정답/오답, 1/5~4/5로 학습): 1/5~4/5 안에서 0.679, 같은 사실 안에서 0.663.
  - P_know (아는 사실 대 모르는 사실): 0.915.
  - axis = h·B: 0.581.
- `gate_simulate.py`: 문턱값과 c를 나머지 4묶음에서 고르고 평가 묶음에 적용한다(중첩). 결과는 1/5~4/5에서 46.7~49.3%로, 모두 밀기(49.2%)와 비슷하다.
- `gate_curves.py`: 예측기 순위 상위 X%만 밀었을 때를 무작위 선택, 오라클과 비교한다.
- P_all이 전체에서 0.936인 것은 대부분 "아는 사실인가"를 맞히기 때문이다. 이 예측기가 틀릴 것 같다고 고르는 행은 대부분 0/5라서 밀어도 고쳐지지 않는다.
- 단서: 디노이징 step 8 상태로는 같은 사실 안 정답/오답 구분이 0.75~0.80이다(`../5_onoff_vs_strength/`). 다만 이때는 답 일부가 이미 채워진 상태다.

## 3. 방향의 모양
- `df_consistency.py`, `df_pairwise.py`: 사실별 차이 d_f(정답 − broken)가 얼마나 일관된지 본다(CPU).
  - d_f의 평균 길이는 16.2이고, 평균 방향의 길이는 4.06이다.
  - d_f 에너지 중 공통 방향에 놓인 몫은 약 13%다. 3,584차원에서 아무 방향이나 하나를 잡으면 약 0.03%다.
  - 개별 d_f끼리의 cosine은 0.02~0.10이다. 그래서 질문 하나만 보고 B로 구별하기는 어렵지만(0.58), 평균 방향으로 밀기에는 충분하다.
- `direction_checks.py` (CPU, 정답/오답 기준, `log_direction_checks.txt`):
  - k별 방향끼리 cosine을 보면 2/5, 3/5, 4/5는 서로 0.81~0.91이다.
  - 1/5는 다른 k와 0.20~0.36이고, 1/5 안에서 반반으로 나눠 구해도 0.40이다. 즉 1/5 방향은 불안정하다.
  - 1/5를 빼고 구한 방향은 전체 방향과 cosine 0.987이다.
  - 5/5 평균 − 0/5 평균 방향은 B와 cosine 0.10~0.17이다. 5/5는 country/capital/sport가 72%이고, 0/5는 director/author/screenwriter/producer가 많아서 관계 차이가 섞이기 때문이다. 관계 안에서 구하면 0.36~0.42가 된다.

## 4. 상태 바꿔치기, 상한 확인 (`patch_upper.py`)
broken 310행의 프롬프트 끝 상태를 다른 질문의 step-0 상태로 통째로 바꿨다(32 forward).

| 넣은 상태 | 정답 |
|---|---|
| 개입 없음 | 3.9% |
| 같은 사실, 정답 질문 | 19.7% |
| 다른 사실(같은 관계), 정답 질문 | 19.7% |
| 같은 사실, entity 오답 질문 | 11.7% |
| 다른 사실, broken 질문 | 13.5% |

- 같은 사실이든 다른 사실이든 정답 질문의 상태면 효과가 같다.
- 이 위치가 담는 것은 사실 정보가 아니라 **"답을 제대로 내는 상태"** 다. 바꿔치기의 평균 변화량은 ‖h_donor − h‖ = 23.8(0.44 × mean‖h‖)이고, B c=1(변화량 54)은 이보다 높은 효과(25%)를 낸다.

## 5. SAE latent로 밀기·빼기 (무작위 latent보다 낫지 않음)
SAE는 16,384개 latent의 JumpReLU이고, 불러오는 코드는 `../sae_io.py`다. 신호 latent를 고르는 방식, 빼는 방식, 더하는 방식을 여러 가지로 바꿔도, **발화율 구간이 같은 무작위 latent를 같은 크기로 빼거나 더한 대조군**과 비슷했다.

| 스크립트 | 신호 / 개입 | 결과 (broken 310행 중 broken으로 남은 비율, 낮을수록 좋음) |
|---|---|---|
| `crossfit_broken.py --nfold 5` (`log_cv5.txt`) | 같은 사실 안 MaxMin 신호 20개를 다른 묶음에서 구해 투영 제거 | 0.806, 무작위 20개 제거 0.752~0.806 (평균 0.783) |
| `pad64_pipeline.py` (`pad64_summary.txt`) | 위와 같고, 저장 답과 같은 배치 64 | 0.839, 무작위 0.810~0.855 |
| `steer_from_0of5.py` (`log_from0of5*.txt`, `log_ratio*.txt`) | 0/5에서만 신호를 찾음(broken 대 entity, 같은 사실 안), 1/5~4/5에 적용 | 0.742~0.848, 무작위 0.65~0.86 |
| `specific_latents.py`, `common_filter.py` | 모든 질문에서 켜지는 latent를 빼고 고름 | 논문의 2% 기준은 후보 0개, 20~50% 기준이 적당. 그래도 무작위와 비슷 |

- **빼는 양이 결과를 정한다.** `removed_energy.py`에서 ‖h‖²을 얼마나 빼는지와 broken 감소의 Spearman 상관이 −0.82(K=5)였다. 투영은 신호 latent를 실제로 꺼 준다(`check_removal.py`, 0.208 → 0.000).
- `steer_broken.py`, `ablate_broken.py`는 대조군이 무작위 가우시안 방향이다. 이 방향은 ‖h‖²의 0.43%만 빼는데, 신호 부분공간은 24.6%를 뺀다(`early_vs_fair.py`). 그래서 이 두 스크립트의 신호 대 무작위 비교는 공정하지 않다.
- 기타 확인:
  - `signal_overlap.py`: 두 절반에서 구한 상위 20개가 8/20만 겹친다.
  - `extreme_signal*.py`: 0/5 broken 대 0/5 entity로 찾은 신호는 같은 사실 안 정답 대 broken을 0.728로 구분한다.
  - `by_commit_time.py`: 답이 개입 구간 안에 정해졌는지로 나눠 봐도 차이가 없다.
  - `sanity_split.py`: 그룹과 부호 점검.
